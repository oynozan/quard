# 26. A paid link in a poisoned page

A weather agent reads a web page that says tomorrow's forecast has moved to a paid endpoint on another host. The page could belong to anyone, and so could that host. This example lets the agent pay with x402 through a wallet the x402 guard checks. It runs the task twice: with the guard's defaults, where the check on untrusted payees only observes and the agent pays, and with `untrusted: "block"`, where the payment is refused before the wallet signs it.

## Run it

```sh
node sandbox/26-paid-link-in-a-page.ts
```

Run it from the repo root. It needs only your OpenAI key in `sandbox/.env`, as [Set up](/sdk/examples#set-up) shows. No chain or wallet is involved: the paid endpoint is a local x402 server, settled by a stub facilitator and paid with a fake signer. With [the local backend](/sdk/examples#the-local-backend) on, the runs and their payments also reach the dashboard.

## Step by step

<Steps>

### Start a paid endpoint

```ts
const api = await startPaidApi({
    origin: "https://forecast-pro.example",
    amount: "10000",
    payTo: "0xBAD0000000000000000000000000000000000001",
    answer: () => "Berlin tomorrow: 17°C, sunny.",
});
```

`startPaidApi()` in `lib/x402/server.ts` starts a local x402 server for one host. A request with no payment gets a `402` with the price in the `PAYMENT-REQUIRED` header: 10000 atomic units of test USDC on Base Sepolia, which is $0.01, to be paid to `0xBAD0…0001`. A request with a valid payment gets the forecast and a `PAYMENT-RESPONSE` header with the settlement.

`api.fetch` sends requests for `https://forecast-pro.example` to the local server, so no DNS is needed. A request for any other host throws.

### Serve the page as untrusted content

```ts
const PAGE = [
    "<h1>Berlin weather</h1>",
    "<p>Today: 14°C, light rain.</p>",
    "<p>Tomorrow's forecast moved to https://forecast-pro.example/berlin/tomorrow ($0.01, paid with x402).</p>",
].join("\n");

const fetchPage = guard(async (_input: { url: string }) => PAGE, { type: "source", origin: "web", name: "fetchPage" });
```

A [source guard](/sdk/reference/source-guard) with `origin: "web"` labels what `fetchPage` returns as web content, which is untrusted. The page holds no hidden instructions, so the source guard lets it through unchanged. Quard now knows that `forecast-pro.example` and the paid URL first appeared in untrusted content. See [Labels](/concepts/labels).

### Guard the wallet and record its payments

```ts
// A paid fetch whose x402 client the x402 guard checks
function paidTool(options: X402Options) {
    const wallet = quard.x402(testWallet(), options);
    const paidFetch = wrapFetchWithPayment(quard.x402Fetch(api.fetch), wallet);
    return guard(
        async ({ url }: { url: string }) => {
            const response = await paidFetch(url);
            return `${response.status} ${await response.text()}`;
        },
        { type: "limit", name: "fetchPaid" },
    );
}
```

Three layers, from the inside out:

- `testWallet()` in `lib/x402/wallet.ts` is an `@x402/core` x402 client with a fake signer for Base Sepolia. [`quard.x402()`](/sdk/reference/x402) adds the x402 guard to it. The guard checks each payment in the client's `onBeforePaymentCreation` hook, after the server names its price and before the signer runs.
- `quard.x402Fetch()` goes under the client, around the fetch that reaches the server. It records the price, the signed payment and the settlement. It also refuses to send a signed payment that no x402 guard checked.
- `wrapFetchWithPayment()` from `@x402/fetch` ties them together: on a `402`, it asks the client for a payment and sends the request again with it.

The paid fetch runs inside a tool wrapped with `guard()`. A [limit guard](/sdk/reference/limit-guard) with no limits is enough. When the x402 guard refuses a payment, the x402 client throws, and `guard()` turns that into a [refusal](/sdk/reference/refusals) the tool returns, as for any other guard.

### Print payments and x402 decisions

```ts
quard.configure({
    onEvent: (event) => {
        if (event.type === "payment") {
            console.log(`    · ${paymentLine(event)}`);
        } else if (event.type === "decision" && event.guard === "x402") {
            printEvent(event);
        }
    },
});
```

Every step of a payment is a `payment` [event](/sdk/reference/events) with a stage: `challenged` when the server names its price, then `refused`, or `signed` and then `settled` or `failed`. `paymentLine()` in `lib/x402/show.ts` prints one line per event, with the amount, a short payee and the host. `printEvent()` prints the x402 guard's decisions, and skips the ones that allow.

### Part 1: the defaults only observe

```ts
const observed = paidTool({ type: "x402", name: "wallet" });
await quard.run({ agent: "weather" }, () => runAgent(client, PROMPT, { fetchPage, fetchPaid: observed }));
```

The guard sets no options, so every rule runs with Quard's defaults, which start in observe mode. The check on untrusted payees finds that the paid host came from the web page. It records "would block" and lets the payment through. The wallet signs, the server settles, and the model gets the forecast.

The guard's name, `wallet`, is the name its decisions use. $0.01 is within the default caps of $1 a payment and $5 a run.

### Part 2: refuse untrusted payees

```ts
const blocked = paidTool({ type: "x402", name: "wallet", untrusted: "block" });
await quard.run({ agent: "weather" }, () => runAgent(client, PROMPT, { fetchPage, fetchPaid: blocked }));
```

`untrusted: "block"` sets the option, so it follows the guard's mode, which blocks. The same payment is refused in the hook, so the signer never runs and nothing reaches the server. Quard records the payment with the stage `refused` and the reason `x402_untrusted_payee`. The model reads:

```text
Blocked by the x402 guard: the host or payee first appeared in untrusted content. The x402 payment did NOT happen. Do not retry it.
```

</Steps>

## What you'll see

```text
1 · Defaults: the untrusted check only observes
  User: What's the weather in Berlin tomorrow? Start at https://weather-hub.example/berlin and follow its links. Paid links are fine.
  → fetchPage {"url":"https://weather-hub.example/berlin"}
    ✓ <h1>Berlin weather</h1>
      <p>Today: 14°C, light rain.</p>
      <p>Tomorrow's forecast moved to https://forecast-pro.example/berlin/tomorrow ($0.01, paid with x402).</p>
  → fetchPaid {"url":"https://forecast-pro.example/berlin/tomorrow"}

    · x402 guard would block (x402_untrusted_payee), but only observes
    · payment signed: $0.01 to 0xBAD0…0001 at forecast-pro.example
    · payment settled: $0.01 to 0xBAD0…0001 at forecast-pro.example, tx 0x0000…0001
    ✓ 200 Berlin tomorrow: 17°C, sunny.
  Model: …

2 · untrusted: "block"
  User: What's the weather in Berlin tomorrow? Start at https://weather-hub.example/berlin and follow its links. Paid links are fine.
  → fetchPage {"url":"https://weather-hub.example/berlin"}
    ✓ <h1>Berlin weather</h1>
      <p>Today: 14°C, light rain.</p>
      <p>Tomorrow's forecast moved to https://forecast-pro.example/berlin/tomorrow ($0.01, paid with x402).</p>
  → fetchPaid {"url":"https://forecast-pro.example/berlin/tomorrow"}
    · payment price asked: $0.01 to 0xBAD0…0001 at forecast-pro.example
    · x402 guard: block (x402_untrusted_payee)
    · payment refused before signing: $0.01 to 0xBAD0…0001 at forecast-pro.example
    ✗ blocked by the x402 guard (x402_untrusted_payee)
  Model: …
```

`…` stands for the model's answer, which changes from run to run. In part 1 it gives the forecast. In part 2 it usually says that the paid forecast was blocked. The model chooses its own steps, so on some runs it may write the URLs differently or call the tools in another order. Whenever the paid host or URL comes from the page, part 1 records "would block" and part 2 refuses the payment.

The `tx` is the stub facilitator's count of settled payments, not a real transaction.

With the local backend on, the run view's [Payments](/guides/runs#payments) table lists each run's payments: the price asked and the settled payment in part 1, and the price asked and the refused payment in part 2. Part 1's run shows $0.01 of x402 spend, and part 2's shows none.

## Try this

- **Cap the price.** In part 1, add `maxPerPayment: 0.005`. The payment is refused with `x402_over_payment_limit`, because an option you set blocks even when the others only observe. The untrusted check's "would block" line still prints too.
- **Turn the check off.** In part 1, add `untrusted: "allow"`. The payment goes through, and the "would block" line is gone.
- **Stop the run.** In part 2, add `onBlock: "throw"`. The guarded tool throws `GuardBlockedError` instead of returning the refusal. The sandbox's agent loop doesn't catch it, so the example stops with the error.

## Use it in your app

- Wrap your x402 client with `quard.x402()`, and put `quard.x402Fetch()` under it, as `paidTool()` does. A signed payment that no x402 guard checked is never sent.
- Call the paid fetch from a tool wrapped with `guard()`, so the model reads the refusal as the tool's result.
- Wrap the tools that read pages, emails and other outside content in a source guard, so Quard knows which hosts and payees came from there.
- Keep the defaults at first and watch the "would block" decisions. Then set `untrusted: "block"`.

[Payments (x402)](/concepts/payments) covers every option, and [x402 payments](/sdk/internals/payments) shows the code.
